## 🐛 **Issues Found**

### **Issue #1: Withdrawal Parsing Error** 🔴

**Severity:** Medium
**Impact:** Cannot import withdrawal history

**Error Message:**
```
✗ Failed to fetch withdrawals: Exchange API error: Failed to parse API response
from /sapi/v1/capital/withdraw/history: error decoding response body.
The API response format may have changed.
```

**Analysis:**
- Binance API for withdrawals may have changed response format
- Model struct `BinanceWithdrawal` likely has field mismatch
- Only affects withdrawals - deposits work fine
- Endpoint: `/sapi/v1/capital/withdraw/history`

**Reproduction:**
```bash
./target/debug/cryptofolio sync-history --account Binance --symbols BTCUSDT
# Always shows withdrawal error
```

**Workaround:** None - withdrawal history cannot be imported

**Recommendation for v0.4.1:**
1. Log actual API response when parsing fails
2. Compare against Binance API docs (2026-03 version)
3. Update `BinanceWithdrawal` struct to match current API
4. Add integration test with live API response

**Priority:** Medium - Not blocking release, but should be fixed soon

---

### **Issue #2: Sync State Not Tracked** 🟡

**Severity:** Low
**Impact:** Incremental sync may re-fetch data unnecessarily

**Observation:**
```sql
SELECT * FROM binance_sync_state;
-- Returns: (empty)
```

After running sync-history, the `binance_sync_state` table remains empty.

**Analysis:**
- MIGRATION_006 created the table correctly
- But sync.rs doesn't appear to populate it
- Incremental sync still works (via external_id duplicate detection)
- Just less efficient than intended

**Impact:**
- Incremental sync works but may make unnecessary API calls
- No data loss or corruption
- Just performance optimization missing

**Recommendation for v0.4.1:**
- Verify sync.rs has code to update sync state
- Add watermark tracking for each record type
- Test that last_trade_sync, last_deposit_sync are populated

**Priority:** Low - Feature works, just not optimally

---

### **Issue #3: Missing Migrations on Upgrade** 🟡

**Severity:** Medium
**Impact:** Existing users upgrading from v0.3.x won't get new tables

**Problem:**
Database created in v0.3.x had migrations 1, 2, 3, 5 applied.
Upgrading to v0.4.0 didn't automatically apply migrations 6, 7, 8.

**Workaround Applied:**
Manually ran migrations 6, 7, 8 via sqlite3 command

**Root Cause:**
- Migration system checks for migration 1 to determine if DB is initialized
- But doesn't check highest applied migration
- Assumes fresh install vs upgrade

**Recommendation for v0.4.1:**
- Improve migration logic to apply missing migrations
- Check for highest applied migration, not just migration 1
- Run any migrations with id > max(id) FROM _migrations

**Code Location:** `src/db/migrations.rs:275-305`

**Priority:** Medium - Fresh installs work fine, but upgrades require manual intervention
