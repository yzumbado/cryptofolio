# v2.0.0 Architecture — Agent-Native Wealth Engine

> Status: **Design / debate capture**. Not yet implemented.
> Supersedes the crypto-only framing of v0.5.0. This document captures the
> architecture debated in the design sessions of 2026-05.

---

## 0. North star

> **Give the agent the tools to handle the *math and bureaucracy* of managing
> wealth, so the human can focus on *strategy and planning to make it grow*.**

cryptofolio v1 is software for a human, with an agent bolted on top. v2 inverts
this: it is software **for an agent**, with the human as the strategist and the
final approver. Every metric, every calculation, every reconciliation is a
deterministic tool call — never something the agent works out in its own
reasoning (where it is slow, expensive, and unreliable).

The product is not a portfolio tracker. It is a **deterministic compute + truth
engine** that an agent drives, covering the user's *entire* balance sheet — not
just crypto.

---

## 1. Scope: the whole balance sheet, not just crypto

v2 tracks everything the user owns and owes, across asset classes with wildly
different liquidity, valuation methods, and refresh cadences.

### Assets
| Class | Examples | Valuation | Typical freshness |
|---|---|---|---|
| Crypto — liquid | exchange + self-custody wallets | market price | minutes |
| Crypto — staked / DeFi | staking, LP, lending (Aave), restaking | accrual + market | hourly / daily |
| Equities | broker accounts, RSUs, options | market price | market hours |
| Fiat / cash | bank accounts, money market | face value + FX | daily / on-demand |
| Fixed income | bonds, treasuries, CDs | yield curve / face | daily |
| Real estate | properties | appraisal / estimate / manual | months |
| Alternatives | commodities, collectibles, private equity | manual / appraisal | irregular |

### Liabilities (first-class, not an afterthought)
| Class | Examples |
|---|---|
| Secured debt | mortgages, auto loans |
| Unsecured debt | credit cards, personal loans |
| Leverage | margin, crypto borrow (the *other* side of Aave) |

**Net worth = Σ assets − Σ liabilities.** A system that only tracks assets is
half a balance sheet. This is a hard requirement, not a future feature.

### Cash flows (balances are not enough)
Dividends, interest, coupons, staking rewards, rent, vesting events. These are
*flows*, tracked separately from balances, and they are what "make it grow."

## 2. The core architecture (debated and locked)

### 2.1 The glue: handles + scalars

The agent's context window is reserved for **decisions and conversation** — never
for data transport.

- **Handles** flow machine-to-machine. A tool returns a *reference* to a result
  set, not the rows.
- **Scalars** flow human-to-machine. Only the specific numbers needed to make a
  decision or speak to the human cross into the agent's context.

The agent holds *names*; the data stays in the engine. This is the opposite of
both naive patterns (Unix-style "agent is the pipe" round-trips, and fat-JSON
"dump everything into context").

### 2.2 Sessions are stateful (decision: B)

Handles persist for the life of a conversation in a **session-scoped handle
table** (closer to a DB cursor / REPL bindings than a Unix pipe). This enables
cheap refinement: "now just the ones over $1k" composes on an existing handle
instead of re-querying from scratch.

Cost of B (accepted): the engine must own session lifecycle, TTL, and garbage
collection, with a `materialize(handle)` escape hatch to freeze rows when the
result must outlive the session.

### 2.3 A handle is a *definition + a pinned version*

Not a snapshot (goes stale silently), not a live view (changes under your feet,
not reproducible). A handle is:

```
set#20 := { def: (positions where apy < 5%), as_of: ledger@v1 }
set#21 := { def: refine(set#20, usd > 1000), as_of: ledger@v1 }   # composes the DEFINITION
```

Consequences — all of them desirable:

1. **Refinement composes definitions, not data.** Cheap; re-evaluable at any version.
2. **Staleness is an explicit contract.** Touching a `v1` handle at `v2` returns
   `{ stale: true, pinned: v1, current: v2, diff: "1 row changed" }`. The agent
   *decides* (re-pin and report the change, or proceed "as of 5 min ago") — a
   judgment surfaced, never a wrong answer buried.
3. **The session is replayable.** A session is a list of query/refine/commit
   definitions with version pins. A human can replay it against `v1` and see
   exactly what the agent saw at each step. The audit log reconstructs the
   agent's *reasoning state*, not just its mutations — which is exactly what a
   human needs when the agent gets something wrong.

### 2.4 Mutations are two-phase

```
draft → validate → (human approves, if irreversible) → commit
```

- **`validate` is a read, not a side-effect.** It re-evaluates the draft against
  the *current* version. (This is the pattern that saved us in practice:
  `"have 5.08, need 10000"` should be a first-class *preview*, not a failed commit.)
- **`commit` is idempotent via `external_id`** (e.g. an on-chain tx hash).
  Re-running is a no-op, not a double-count. This is the real fix for the
  `cost_basis_only` footgun in v1 — idempotency instead of a band-aid flag.
- **No irreversible action fires against a stale pin.** A decision made `as_of v1`
  is re-validated at commit; if the underlying changed, the agent stops and re-asks.

### 2.5 Verbs, not queries (decision: i)

The definition language is a **closed set of typed verbs**
(`query / refine / aggregate / top / compare / …`) with fixed predicates — *not*
an embedded DSL the agent writes freely.

Rationale: the failure mode of a free query language (agent emits a subtly wrong
query, engine executes it *precisely*, produces a confident-but-wrong answer) is
the exact thing this whole architecture exists to prevent. One deliberate
`materialize()` escape hatch covers the long tail. Revisit (ii) only if the
expressiveness wall is hit repeatedly in practice.

### 2.6 Error contract

Every error is typed and **contains the fix**. Good: `{ INSUFFICIENT_BALANCE,
have: "5.08", need: "10000" }`. Bad: an opaque failure that forces the agent to
guess valid inputs (e.g. trying `account_type` three times). Errors enumerate
valid inputs and the corrective action.

## 3. The refresh / freshness architecture

The user's insight: *"a similar architecture to keep the portfolio fresh,
refreshing multiple times a day or per request."* This maps directly onto §2.3.

- Each **data source** (exchange API, chain RPC, price oracle, FX feed, bank
  connector, broker connector, real-estate estimate) has a **refresh policy**:
  a cadence and a confidence.
- A refresh **advances the ledger watermark** (`v1 → v2`). That is the *only*
  thing a refresh does to the model — bump the version and write new values.
- Handles pinned to `v1` then become detectably stale (§2.3.2). "Refresh" and
  "staleness" are two ends of the same mechanism.

**Freshness is per-asset-class, and that's the point:**

| Source | Cadence | Staleness that matters |
|---|---|---|
| Crypto price | minutes | an hour is meaningful |
| Equities | market hours only | overnight gap is expected |
| FX | hourly | low volatility, tolerant |
| Staking accrual | daily | rewards tick slowly |
| Bank balance | daily / on-demand | rarely intraday |
| Real estate | quarterly / manual | months-stale is *normal* |

Each asset therefore carries **`valuation_method + confidence + as_of`**. Real
estate being "stale" for three months is fine; crypto stale for an hour is not.
The staleness contract already models this — confidence and cadence are just
metadata on the handle's version pin.

## 4. What we are still missing (gaps to resolve)

Beyond the asset classes already listed, these are not yet designed:

1. **Liabilities & net worth** — promoted to §1, but the debt-side data model
   (amortization, interest accrual, the asset/borrow duality of DeFi lending)
   is undesigned.
2. **Multi-currency / FX normalization** — a base currency, per-account native
   currencies, FX as a first-class refresh source. Pervasive once banks are in.
3. **Cash-flow / income ledger** — dividends, interest, rent, rewards, coupons as
   *flows* distinct from balances. Required to answer "is it growing?"
4. **Tax lots & jurisdictions** — per-lot cost basis, holding period
   (short/long), taxable vs tax-deferred accounts, wash-sale rules. Tax
   treatment differs by asset class *and* account type.
5. **Corporate / on-chain actions** — splits, mergers, spinoffs, airdrops, token
   migrations. (We already hit token-migration ambiguity with TAO/RPL.)
6. **Connectivity / the truth layer** — Plaid-class connectors for banks &
   brokers, exchange keys, chain indexers, real-estate estimates. **This is 80%
   of the work** (see §5).
7. **Security model** — aggregating bank + broker + crypto is a high-value
   target. Read-only credentials only; never withdrawal-capable keys; encryption
   at rest; clear blast-radius boundaries.
8. **Strategy layer** — target allocation, drift detection, rebalance proposals,
   scenario/what-if modeling, goal tracking. This is where the north star
   actually lands; everything above is plumbing for it.

## 5. The honest risk: truth, not math

The architecture in §2 is the *elegant* layer and is a few weeks of clean work.
**The moat and the risk both live in the truth layer**, not the compute layer.

Evidence from real use (2026-05): a crypto Earn position could not be reconciled
(`[private]` displayed vs `[private]` from the API; Earn reward endpoints 404'd).
No amount of handle-elegance fixes incomplete truth. Built on a flaky truth
layer, this architecture produces *precise, composable, replayable, confidently
wrong* answers — strictly more dangerous than a messy tool, because the polish
makes the wrongness trustworthy.

**Design principle:** every value carries provenance and confidence, and the
agent must be able to say "I can't reconcile this" as a first-class outcome —
never paper over a gap with a computed guess.
